# Ответы на вопросы лабораторной работы

## 2.1. Нужны ли стайлгайды? Всегда ли они необходимы?

Стайлгайды **нужны**, когда документацию пишут несколько людей, она живёт долго и должна звучать как один продукт. Они снижают споры на ревью («как правильно?»), ускоряют онбординг и делают Docs as Code управляемым: правила можно проверять линтерами и чек-листами.

**Не всегда обязательны.** Для одноразовой заметки одного автора или прототипа на выходные формальный стайлгайд избыточен. Достаточно короткого README «как пишем». Имеет смысл вводить стайлгайд, когда появляются повторяющиеся замечания на ревью, растёт число авторов или документация становится частью продукта для внешних пользователей.

**Вывод:** стайлгайд — инструмент масштаба и качества, а не самоцель. Нужность определяется числом авторов, сроком жизни документов и требованиями к единообразию.

## 2.2. Как использовать стайлгайд при разработке документации?

Примеры:

1. **Чек-лист перед PR** — автор сверяет тон, термины, структуру типа документа (tutorial / how-to / reference).
2. **Основа для шаблонов** — шаблон «Как сделать X» уже содержит блоки: цель, предусловия, шаги, результат.
3. **Критерии ревью** — ревьюер ссылается на конкретный пункт («см. Терминология: не писать „юзер“»), а не спорит вкусом.
4. **Онбординг** — новый разработчик читает 5–10 страниц стайлгайда вместо «посмотри, как у нас принято».
5. **Автопроверки** — часть правил переносится в markdownlint / Vale (длина заголовков, запрет «здесь», стиль списков).
6. **Согласование терминов** — изменения продукта сначала попадают в словарь стайлгайда, потом в пользовательские тексты.

## 2.3. Как использовать ИИ при разработке стайлгайда?

- **Сбор черновика структуры** — попросить модель предложить оглавление по аналогам (Google, Microsoft, Write the Docs).
- **Генерация примеров «хорошо / плохо»** — на основе уже принятых принципов.
- **Проверка черновиков документов** — «проверь текст на соответствие этим правилам» (правила вставить в промпт или RAG).
- **Поиск противоречий** — сравнить разделы стайлгайда между собой.
- **Локализация формулировок** — упростить канцелярит, предложить альтернативы из таблицы «избегать / предпочитать».

Ограничение: ИИ не заменяет владельца стайлгайда. Финальные правила утверждает команда; модель может предложить шум или чужие конвенции. Секреты и внутренние названия продуктов в публичные модели не отправляют без политики компании.

## 3. Объект стайлгайда

**Объект:** техническая документация программного продукта класса веб/SaaS-приложения.

В область входят:

- пользовательские how-to и tutorials;
- документация API и примеры интеграции;
- README, CONTRIBUTING, CHANGELOG репозиториев продукта;
- release notes.

Вне области: маркетинг, юридические тексты, UI-дизайн-система.

## 4.1. Структура правил (какие вопросы закрывает стайлгайд)

Стайлгайд отвечает на вопросы:

1. Для кого и какие типы документов пишем?
2. Какой тон, лицо, время глаголов?
3. Как строить документ (обязательные блоки, типы Diátaxis)?
4. Как оформлять Markdown, UI-элементы, ссылки, таблицы?
5. Какие термины каноничны?
6. Как писать и помечать примеры кода?
7. Как формулировать заголовки и списки?
8. Как проверять доступность текста? *(раздел добавляется в PR)*
9. Как предлагать изменения в сами правила?

Важно при составлении: правила должны быть **проверяемыми**, с примерами, без вкусовщины; приоритет при конфликтах зафиксирован.

## 4.2–4.4. Правила и структура стайлгайда

Правила зафиксированы в разделах сайта:

| Раздел | Содержание |
| --- | --- |
| О стайлгайде | Назначение, область, как пользоваться |
| Язык и тон | Обращение, ясность, англицизмы |
| Структура документов | Типы, блоки, имена файлов |
| Форматирование | Markdown, ссылки, admonitions |
| Терминология | Словарь и процесс обновления |
| Примеры кода | Полнота, секреты, версии |
| Заголовки и списки | Иерархия, чек-листы |
| Примеры | README и how-to по правилам |
| Доступность текста | *(ветка / PR — задание 11)* |

Иерархия сайта задана в `mkdocs.yml` → `nav`.
