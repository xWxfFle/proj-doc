# Доступность текста

Правила помогают читать документацию людям с разной подготовкой и при использовании вспомогательных технологий.

## Язык и сложность

- Предпочитайте короткие предложения: старайтесь не превышать 25 слов. Это ориентир, а не жёсткий лимит — не дробите мысль, если предложение и так легко читается.
- Одна инструкция — один шаг нумерованного списка.
- Раскрывайте аббревиатуры при первом упоминании: «интерфейс программирования приложений (API)».
- Не полагайтесь только на цвет: пишите «ошибка» текстом, а не «смотрите на красное».

## Структура для скринридеров

- Соблюдайте иерархию заголовков без пропусков уровней.
- Текст ссылок формулируйте полной фразой и так, чтобы он был понятен вне контекста: «откройте [правила доступности текста](accessibility.md)», а не «нажмите здесь».
- Для изображений указывайте осмысленный `alt`:

```markdown
![Страница создания проекта: поле «Название» и кнопка «Сохранить»](images/create-project.png)
```

- Декоративные изображения помечайте пустым alt: `![](divider.png)` или не включайте в контент.

## Таблицы и списки

- В таблице всегда есть строка заголовков:

```markdown
| Параметр  | Тип    | Описание                  |
|-----------|--------|---------------------------|
| `name`    | строка | Название проекта          |
| `private` | булево | Скрыть проект от поиска   |
```

- Не используйте таблицы для вёрстки абзацев.
- Длинные процедуры дробите на списки — так проще навигировать со скринридером.

## Контраст и оформление в UI-доке

- Если вставляете скриншот, кратко передайте его ключевой смысл текстом рядом: что нужно увидеть или сделать. Не пересказывайте изображение дословно.
- Не делайте инструкцию вида «нажмите на зелёную кнопку справа» без названия кнопки.

## Проверка перед публикацией

- [ ] Заголовки идут по порядку H1 → H2 → H3
- [ ] У всех смысловых изображений есть alt
- [ ] Ссылки названы по смыслу страницы
- [ ] Критичные шаги понятны без скриншота
- [ ] Нет инструкций, завязанных только на цвет или положение «справа в углу»
