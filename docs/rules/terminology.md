## Словарь продукта (фрагмент)

| Термин | Значение | Не писать | Пример фразы |
| --- | --- | --- | --- |
| Организация | Юридическое или командное пространство в продукте | Компания, тенант (в пользовательских текстах) | «Создайте организацию для команды разработки.» |
| Проект | Рабочая единица внутри организации | Репозиторий (если речь не о Git) | «Добавьте проект “Мобильное приложение”.» |
| Участник | Пользователь с ролью в организации | Юзер, аккаунт | «Пригласите участника с ролью Редактор.» |
| API-ключ | Секрет для программных запросов | Токен (если это именно key) | «Создайте API-ключ для CI-пайплайна.» |
| Вебхук | HTTP-уведомление о событии | Callback (в пользовательской доке) | «Подпишитесь вебхуком на событие `project.created`.» |

## Правила именования

- UI-элементы пишите так, как они подписаны на экране: кнопка **Создать проект**.
- Имена API-полей пишите как в схеме и в backticks: `project_id`.
- Не смешивайте «логин» и «войти»: для действия используйте **Войти**, для поля — **Электронная почта**.

Примеры:

| Контекст | Правильно | Неправильно |
| --- | --- | --- |
| Кнопка в UI | Нажмите **Создать API-ключ**. | Нажмите кнопку создания. |
| Поле API | Передайте `owner_id` в теле запроса. | Передайте id владельца как угодно. |
| Экран входа | Введите адрес в поле **Электронная почта** и нажмите **Войти**. | Залогиньтесь в аккаунт. |

## Согласование новых терминов

1. Проверьте, нет ли термина в словаре.
2. Предложите термин в PR с обоснованием и 1–2 примерами фраз.
3. После merge обновите эту страницу.

Пример обоснования в PR: «Предлагаю термин “рабочая область” вместо “workspace” в пользовательской документации, потому что так подписан пункт меню.»
